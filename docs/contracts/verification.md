# Contract: Independent Verification Engine

**Status**: `ACTIVE (Implemented)` — `backend/verification/` (`StaticVerifier`, `DynamicVerifier`, `ContractVerifier`, `Judge`, `VerificationOrchestrator`), wired at `POST /api/v1/pipeline/task/{task_id}/execute` and `.../repair`.

## 1. Purpose
Defines the verification engine responsible for validating that code changes generated by the implementation engine compile, pass automated tests, satisfy linting rules, and do not introduce regressions.

## 2. Verification Steps
1. **Syntax & AST Validation** (`StaticVerifier`):
   - Parses modified files (AST for Python, regex-based import resolution for TS/JS) to verify zero syntax errors and that all imports resolve against the repo's manifest / local file tree. Runs on the host — pure inspection, no code execution.
2. **Automated Test Execution & Build** (`DynamicVerifier`):
   - Runs `pytest` (Python) and `npm run build` (Node/TS) **inside an isolated container sandbox** (`backend/verification/docker_runner.py::DockerVerificationRunner`, image `docker/verification.Dockerfile`) — the container that actually executes the code the agent just wrote, bind-mounted to the worktree, non-root, resource-capped, with a hard timeout. Falls back to host subprocess execution only if the Docker daemon is unavailable (`settings.verification_use_docker`). See `ARCHITECTURE.md` §4 for the full isolation-model rationale (this is the only step of the pipeline that runs inside a container — the agent's code-writing step stays a plain git worktree, per `agent.md` / `implementation-contract.md`).
   - Type checking / linting (`mypy`/`tsc`, `ruff`/`eslint`) as dedicated tools is not yet implemented — currently `npm run build` implicitly surfaces TS type errors.
3. **Contract Coverage** (`ContractVerifier`):
   - Checks the diff against the `ImplementationContract`'s invariants and required tests.
4. **Regression Analysis**: not yet implemented — no comparison against a pre-modification test baseline exists yet.

## 3. Output Contract
- Emits a `VerificationReport` (`backend/verification/schemas.py`) aggregating all three vectors, with status (`PASS` / `FAIL` / `ERROR` / `UNVERIFIED`), execution time, itemized `Defect`s (category, file, line, severity), and an evidence manifest.
- Every verification run also emits `VERIFICATION_STARTED`/`VERIFICATION_COMPLETED` `AgentEvent`s and, on repair, `REPAIR_STARTED` — persisted and streamed per `DATA_MODEL.md` §1.5 / `API.md` §8.
